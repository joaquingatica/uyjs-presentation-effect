## Presentando: efectos

Usamos el concepto de un **efecto** que **declare** lo que va a suceder y
qué necesita para que suceda.

<v-click>

Es el _tipo base_ del framework:

```ts
//            ┌─── Tipo del resultado
//            │        ┌─── Tipo del error
//            │        │      ┌─── Las dependencias
//            ▼        ▼      ▼
type Effect<Success, Error, Requirements>
```

</v-click>

<v-click>

Que se puede entender como:

<!-- prettier-ignore-start -->
```ts
type LazySafePromise = (context: Requirements) => () => Promise<Result<Success, Error>>
```
<!-- prettier-ignore-end -->

<sub>
* Disclaimer: es una sobre-simplificación, pero ilustrativa
</sub>

</v-click>

## Creando Effects

Declarando un comportamiento sin ejecutarlo aún.

```ts
type Effect<Success, Error, Requirements>
```

<br />

::left::

```ts {1,2|4-5|7-11|13-17}
// Effect<string, never, never>
const program = Effect.succeed('Hello World!')

// Effect<never, ParseError, never>
const program = Effect.fail(new ParseError('Invalid'))

// Effect<User, ParseError | HttpError, HttpClient>
const program = Effect.gen(function* () {
  const data = yield* fetchUsers
  return yield* parseUserFromData(data)
})

// Effect<User[], DbError, DbService>
const program = Effect.gen(function* () {
  const { getUsers } = yield* DbService
  return yield* getUsers()
})
```

::right::

<v-click>

Utiliza generators para **componer y establecer
dependencias** entre effects.

`yield*` "pide" resultado de otro `Effect`.

Similar al `await` de una `Promise`.

</v-click>

## Ejecutando Effects

Un `Effect` describe, el framework lo ejecuta. ¿Cómo?

<v-click>

Opción 1) Agnóstico a la plataforma:

```ts {hide|3-4|6-7}
const program = Effect.succeed(1)

// result: number
const result = Effect.runSync(program)

// result: Promise<number>
const result = Effect.runPromise(program)
```

</v-click>

<v-click>

Opción 2) Específico a una plataforma:

```ts {hide|1|5}
import { NodeRuntime } from '@effect/platform-node'

const program = Effect.succeed(1)

NodeRuntime.runMain(program)
```

</v-click>

## Desmitificando el `pipe`

Es una forma de **componer funciones** de manera legible.

::left::

<v-click>

<!-- prettier-ignore-start -->
```ts
// Encadenamiento de métodos + variables intermedias
const yearString = 'mvd js 2025 '
  .trim()
  .slice(-4)

const year = Number.parseInt(yearString, 10)

// year: 2025
```
<!-- prettier-ignore-end -->

Funciona con métodos del `prototype`.

</v-click>

::right::

<v-click>

<!-- prettier-ignore-start -->
```ts
// Composición de funciones
const year = pipe(
  'mvd js 2025 ',
  trim,
  slice(-4),
  parseInt(10)
)
// year: 2025
```
<!-- prettier-ignore-end -->

Funciona con **cualquier función**, no solo métodos.

Dato fluye de **izquierda a derecha**.

Las funciones tienen **firmas compatibles**.

Las funciones **transforman** el dato "mientras fluye".

<sub>

\* Existe un [ECMAScript Proposal](https://github.com/tc39/proposal-pipeline-operator) para un pipe operator "|>".

</sub>

</v-click>

## Effect × pipe

En Effect, `pipe` es la forma de **componer y transformar** datos y efectos.

<v-clicks>

<<< @/snippets/overview-pipe-effect.ts#snippet {all}

**Ventajas:**

- 🧠 Menos carga cognitiva (no hay que nombrar intermedios)
- 💉 Fácil inyectar y modificar comportamiento
- ⭐️ Funciones puras y componibles
- 👷‍♀️ Equivalente funcional del Builder pattern

</v-clicks>

## Analicemos

Veamos en detalle un código casi production-ready:

```ts {hide|all|3,4|5,12|5,6,12|5,7,12|5,8,12|5,9,12|5,10,12|5,11,12|all}
import { Effect, pipe } from 'effect'

// Effect<SmsResult, UserError, DbService | SmsService>
const sendSmsToUser = (userId: string) =>
  pipe(
    userId,
    getUserById,
    Effect.andThen(sendSms),
    Effect.retry({ times: 3 }),
    Effect.tap(Effect.log('User notified successfully!')),
    Effect.catchTag('SmsError', () => Effect.succeed(SmsResult.Failed))
  )
```
